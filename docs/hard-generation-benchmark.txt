Controlled classic/king hard benchmark
=====================================

This is a reproducible Node generation comparison, not Windows/browser UI testing.
It never changes product source, settings, saved games or the older checkout.

Provide the complete previously delivered v5 source directory, including its
recorded docs/diversity-audit/v5-audit-30.json report. The report is needed to
reconstruct real historical recent-key ledgers; an empty approximation is not used.

Plan only (does not run generation):
  HARD_BENCH_BASELINE=/path/to/NineRealms-v5 node scripts/benchmark-hard-generation.cjs

Full comparison after both algorithms are frozen:
  HARD_BENCH_BASELINE=/path/to/NineRealms-v5 node scripts/benchmark-hard-generation.cjs --run
  node scripts/summarize-hard-benchmark.cjs

Optional environment values:
  HARD_BENCH_SAMPLES=200         independent new seeds per mode (default 200)
  HARD_BENCH_ARM=paired          paired / baseline / candidate
  HARD_BENCH_OUTPUT=hard-ab-200.json
The current checkout is the candidate. An explicit baseline directory avoids any
need for the developer's original workspace paths or directory layout.

Protocol
--------
- 200 independent prespecified new seed strings for each of classic/king hard.
- Two old failures are SEPARATE regression cases, not mixed into those 200:
  fresh-quality-v4-classic-14 and fresh-quality-v4-king-17.
- Their original recent ledgers are rebuilt from all earlier successful records,
  preserving actual deduplication/order and the 256-key cap (28 and 256 keys).
- The new-seed cohort uses the original pre-mode ledger as a fixed experimental
  condition. Both arms receive byte-identical requests; per-arm evolving ledgers
  are deliberately avoided because divergent outputs would confound comparison.
  This is an independent-seed study, not a continuous-session history simulation.
- Each module receives the same recorded easy/hard warmup requests. Validation
  runs in a third isolated VM using frozen v5 Engine/Hints/canonicalizer source,
  so neither arm gets extra generation-engine warming from validation work.
- Generation is serial. Within EACH mode, arm order alternates AB / BA by seed
  index. No concurrent browser/load or full regression test should be scheduled.
- Every call records wall time, process CPU time, load average, result or refusal,
  source hashes, request hash, and the complete original returned puzzle before
  validation. SHA-256 source snapshots are compared at end; drift invalidates a
  final comparison rather than being silently ignored.

Verification and reporting
--------------------------
Completed boards/givens must be legal under the frozen engine. A separate bounded
uniqueness search must prove exactly one answer without budget exhaustion. The
independent Hints proof gets maxSteps=200 and timeLimitMs=1000, must actually solve
and use a hard-tier supported technique, and its trace must reconstruct the unique
answer. Density, a hard label, or a partial proof alone cannot pass this check.
Complete classical-group signatures detect repeated bases within each arm.
Matching signatures BETWEEN baseline and candidate are expected and not duplicates.

Generation refusal, explicit generation budget, validation budget, stalled proof,
wrong tier, invalid output, unexpected error and valid strict-hard are distinct.
A single unresolved verification issue is retained, not counted as valid hard.
All timing percentiles include ALL requests; verified-only and refused-only timing
are also reported separately. The summary adds mean/P50/P95/P99/min/max, paired
improvements and regressions with all affected seed IDs, and shared-request checks.
Above-8000ms calls are not counted as within-watchdog completions. Even faster
synchronous calls do not prove UI delivery or performance on the user's device.
One timing observation per seed/arm is not a hardware certification or a formal
statistical significance claim.

Outputs
-------
  evidence/hard-generation/hard-ab-200.json          complete original evidence
  evidence/hard-generation/hard-ab-200-summary.json  derived summary + raw SHA
The benchmark checkpoints every ten cases. Incomplete reports must not be called
final. No seed is discarded or replaced because its result is inconvenient.

Candidate 2 protocol (prepared; do not run until the algorithm is frozen)
-----------------------------------------------------------------------
Use fresh, predeclared v2 seeds for the main comparison. This avoids presenting
training-on-v1 repairs as evidence of general improvement. Four regression cases
are reported separately: the two original failures with exact original ledgers,
and v1 classic 105 / 168 with empty ledgers. No existing report is overwritten.

  HARD_BENCH_BASELINE=/path/to/NineRealms-v5 HARD_BENCH_SEED_NAMESPACE=v2 HARD_BENCH_OUTPUT=candidate2-hard-ab-v2-200.json node scripts/benchmark-hard-generation.cjs --run
  node scripts/summarize-hard-benchmark.cjs evidence/hard-generation/candidate2-hard-ab-v2-200.json

This is 808 timed calls: 400 independent seed pairs plus four regression pairs.
Omit --run to inspect the plan only, without loading or running generation.

Additionally replay the original 400 independent v1 requests candidate-only:

  HARD_BENCH_BASELINE=/path/to/NineRealms-v5 HARD_BENCH_ARM=candidate HARD_BENCH_REPLAY_REPORT=docs/hard-generation-audit/candidate1-hard-ab-200.json HARD_BENCH_OUTPUT=candidate2-v1-replay.json node scripts/benchmark-hard-generation.cjs --run
  node scripts/summarize-hard-benchmark.cjs evidence/hard-generation/candidate2-v1-replay.json

Replay copies exact archived requests/ledgers rather than reconstructing them
from current defaults. Its source report SHA is recorded. replayComparison lists
all outcomes, matching request hashes, newly fixed seeds and reverse regressions
against candidate 1. Replay timings are not simultaneous paired A/B timings and
must not be presented as such. The independent v2 cohort remains the principal
comparison. Archived candidate 1 evidence and generator snapshot remain intact.
